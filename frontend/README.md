# PRISM — Environmental Intelligence Control Centre

A React/TypeScript multi-hazard monitoring dashboard by Team PRISM (SMVDU) for Make-a-Thon '26. **Student prototype; not a certified warning service.**

## Requirements

- Node.js 20.19+ or 22.12+
- npm and internet access for the **first** installation of dependencies
- Optional FastAPI backend on port 8000

## Start

```bash
cd frontend
cp .env.example .env  # PowerShell: Copy-Item .env.example .env
npm install
npm run dev
```

Open `http://localhost:5173`. Select **Demo** to navigate all pages without any backend. `npm run test:demo` validates all eight scenarios; `npm run build` creates production files in `dist/`; `npm run preview` serves that build.

> `package-lock.json` is generated by the first `npm install` and should be committed once dependency installation is possible. No lockfile with fabricated dependency integrity hashes has been supplied.

## Eight pages

| Route | Functional features |
|---|---|
| `/` | Overall risk dial, 5 hazard cards, 7 sensor tiles, interactive demo scenario picker, risk and station visualizations, recent alerts/events |
| `/monitor` | Sensor/site filters, 15m/1h/6h/24h/custom range, summary stats, time series, quality/freshness table, manual refresh |
| `/risk` | Hazard selector, contributing readings, explanations, trajectories, recommended actions, cross-hazard comparison |
| `/map` | OpenStreetMap + Leaflet station markers, risk and deployment filters, popups, detail panel, zoom/pan |
| `/reports` | Date/site/hazard/severity filters, alert and event breakdowns, sensor trend, print layout, CSV export |
| `/events` | Search, filters, time range, pagination, detail dialog, CSV export with original timestamps |
| `/alerts` | Queue, details, filters, simulated notification statuses, demo test alerts, acknowledge, confirm resolution |
| `/settings` | Demo/live switching, configurable API URL, backend test, refresh frequency, display density, station selection |

## Demo training scenarios

Normal conditions; increasing rainfall/water level; slope instability; urban drainage flooding; anomalous ground motion (NOT earthquake prediction); stale/disconnected sensors; escalating risk; alert workflow training. These are **deterministic simulated readings**, not historical physical measurements. Scenario selection updates the same shared frontend snapshot across pages. Demo alerts can be acknowledged, resolved, and generated, with corresponding event history. Changing scenarios resets their demo history.

## Live backend integration

Set `VITE_API_BASE_URL=http://localhost:8000` in `.env`, or update the base URL under Settings. Switch to **Live API**. The typed client in `src/services/api/client.ts` attempts these expected endpoints: `/health`, `/api/v1/sites`, `/api/v1/devices`, `/api/v1/readings/latest`, `/api/v1/risk/current`, `/api/v1/alerts`, `/api/v1/events`, plus `/api/v1/readings/history` for detailed telemetry. Requests time out after eight seconds. The backend should permit your frontend origin with an appropriate CORS policy. Missing/invalid values are never silently substituted with zeros. Live errors are visible and no fallback data is injected.

**Important:** The actual backend `API_CONTRACT.md` was **not** supplied. Endpoint names and field transforms are provisional. Before live deployment, reconcile payload shapes, timestamps, pagination, authentication and command semantics with the actual contract. Live acknowledge/resolve/test-alert writes are deliberately disabled until documented. WebSocket/SSE stream parsing is not implemented without an agreed event schema; interval polling works for available endpoints. Live reports lack historical trend series except for the readings/history endpoint on Live Monitor. Backend responses are subject to basic runtime validation, but are not a substitute for final contract-level schema validation. Real weather/terrain/satellite integrations and notification delivery receipts depend on separately developed services.

### Expected example shapes (provisional, not authoritative)

```json
{ "id": "SITE-001", "name": "Slope Node", "location": "Region", "latitude": 32.99, "longitude": 74.94, "deployment": "Hillside / slope", "device_status": "online", "last_updated": "2026-10-19T06:00:00Z" }
```

```json
{ "site_id": "SITE-001", "sensor_type": "rainfall", "value": 12.5, "unit": "mm/h", "previous_value": 10.1, "timestamp": "2026-10-19T06:00:00Z", "status": "online" }
```

```json
{ "id": "flash_flood", "score": 43, "trend": "increasing", "factors": ["Rainfall is rising"], "timestamp": "2026-10-19T06:00:00Z", "source": "backend" }
```

Risk thresholds are demonstrative: 0–30 NORMAL, 31–50 WATCH, 51–75 WARNING, 76–100 CRITICAL. They have not been calibrated or certified. Overall risk is the maximum available hazard score, **not** a probabilistic forecast. Map risk markers use demonstrative per-site hazard scores or backend-provided `hazard_scores`; missing per-site scores appear as unknown rather than borrowing network risks. Arbitrary hazard zones are not drawn. An anomalous vibration sensor cannot reliably predict earthquakes.

## Architecture

- `src/context/PrismContext.tsx` — central source state, polling, demo mutations, local preferences
- `src/services/demo/data.ts` — deterministic scenarios, historical sample generator
- `src/services/api/client.ts` — central typed adapters, request deadlines, basic response validation
- `src/components/layout/` — reusable sidebar, responsive global navigation
- `src/components/common/` — reusable badges, cards, controls, states
- `src/components/charts/` — Recharts visualizations
- `src/components/maps/` — React Leaflet + OpenStreetMap
- `src/pages/` — eight dedicated routes
- `src/types/`, `src/utils/` — types and shared helpers

## Environment and privacy

Any `VITE_` environment variable is visible to browser clients. Do not put API keys, private device credentials, SMTP tokens or SMS provider secrets into client code or `.env` under `VITE_`. Implement secrets, device authentication, backend mutation permissions, provider receipts and warning distribution on the server.

## Limitations and remaining validation

First dependency installation and `npm run build` require npm registry access. If run in a restricted sandbox without network/package cache, installation/build verification cannot succeed; run the documented commands on a connected development system. Test each route and device form factor there, including Leaflet tile accessibility. These source files were authored in an environment with no npm registry access, so a passing production build is **not claimed**.
